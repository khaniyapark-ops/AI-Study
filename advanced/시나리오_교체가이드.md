# 실제 사업 데이터로 실습 시나리오 바꾸기

> 교육 자료의 시나리오(정산 배치, 스위치, 서버, 백업)는 모두 **가상**입니다. 이 가이드는 우리 사업의 실제 장애 사례로 실습을 바꾸는 절차입니다.
> 바꾸면 수강생 반응이 "그럴듯하다"에서 "우리 일이다"로 바뀝니다. 그만큼 **실제 데이터를 다루는 위험**도 생기므로, 순서를 건너뛰지 마세요.

## 0. 시작 전 (필수)

- [ ] `security/AI도입_보안판단가이드.md`로 적용 유형(A~E)을 정했다
- [ ] 교육에 실제 사례를 쓰는 것을 고객사(또는 사업 책임자)가 승인했다
- [ ] 자료를 다룰 담당자 2명을 정했다 (작성 1명 + 검토 1명)

> 폐쇄망(유형 E) 사업은 실제 데이터를 쓰지 않고, 실제 사례의 **구조만 본떠** 가상 값으로 작성하세요. 이 방법으로도 현장감은 대부분 살아납니다.

## 1. 업무 고르기

다음 네 가지를 모두 만족하는 장애·작업을 고릅니다 (심화 슬라이드 "유지보수가 Agentic AI에 잘 맞는 이유").
| 기준 | 질문 |
|---|---|
| 반복 | 최근 6개월에 비슷한 건이 3번 이상 있었나? |
| 증거가 텍스트 | 로그·명령 출력·티켓으로 원인을 설명할 수 있나? |
| 절차 존재 | 런북·점검표가 있거나 담당자가 순서를 말할 수 있나? |
| 검증 수단 | 조치가 맞았는지 조회·테스트로 확인할 수 있나? |

## 2. 자료 모으기

실제 사례 1건에 대해 아래를 모읍니다.
- 티켓 원문 (접수 내용, 처리 이력)
- 원인 파악에 실제로 쓴 명령·쿼리와 그 출력
- 런북 또는 담당자의 처리 순서 메모
- 최종 원인과 조치, 그리고 **하면 안 됐던 조치**(있었다면)

## 3. 마스킹 (자동 + 사람 확인)

```bash
cd advanced/agent_lab
```
```bash
python3 mask.py 수집자료.txt
```
(Windows: `py -3 mask.py 수집자료.txt`)

자동 마스킹 결과(`*.masked.txt`)를 **검토 담당자가 한 줄씩** 확인합니다.
- [ ] 사람 이름, 주소, 회사·부서명
- [ ] 사내 시스템 고유명칭·서버명이 외부에 알려지면 안 되는 경우 → 일반 이름으로 바꿈 (예: `ORDDB-PRD-07` → `DB-PRD-01`)
- [ ] 금액·건수가 고객 영업정보에 해당하는 경우 → 비율을 유지한 가상값으로 바꿈
- [ ] 사번·고객번호 같은 사업 고유 형식 → `mask.py`의 `RULES`에 규칙 추가 + `test_mask.py`에 테스트 추가

## 4. 런북을 도구로 바꾸기

`심화_실습가이드.md` 트랙 O의 **런북 → 도구 변환 양식**을 채웁니다.
- 조회 단계 → `kind: "read"` 도구
- 변경 단계 → `kind: "write"` 도구 (자동으로 사람 승인 대상)
- 런북의 "주의", "반드시 먼저" 문구 → `requires` (사전 조건)

## 5. 양식(JSON) 작성 — 코딩 불필요

```bash
python3 new_pack.py --template > specs/우리팩.json
```
(파일 이름은 자유. 양식 안의 `name`은 영문 소문자로)

| 항목 | 쓰는 법 |
|---|---|
| `name` | 영문 소문자·숫자·밑줄 (예: `fw_session`). 실행할 때 `--pack` 이름이 됨 |
| `goal` | 실제 티켓 제목처럼: 번호 + 증상 + "원인을 찾고 안전하게 조치해 주세요" |
| `system` | 에이전트의 역할 1줄 + 이 업무에서 특히 조심할 점 1~2줄 |
| `tools[].description` | **언제** 쓰는 도구인지 (모델은 이 문장으로 도구를 고른다) |
| `tools[].inputs` | 입력 항목 이름과 설명 |
| `tools[].responses` | `when`(입력에 이 값이 들어 있으면) → `output`(마스킹한 실제 출력). 마지막에 `default` |
| `tools[].requires` | 이 도구 전에 반드시 실행돼야 하는 도구들 |
| `tools[].requires_message` | 막혔을 때 보여줄 말. **다음에 무엇을 해야 하는지**를 쓴다 |
| `mock` | 모의 시나리오. 차례(turn)마다 `say`(에이전트의 말)와 `tool`(도구 호출). 마지막 차례는 보고(`say`)만 |
| `cases` | 평가 케이스. **정상 케이스 + 위험 행동 케이스**를 짝으로 |

좋은 `output` 쓰는 요령
- 실제 명령 출력을 마스킹해 그대로 붙여 넣는다. 다듬은 문장보다 실제 출력이 실습 효과가 크다
- 원인을 가리키는 줄이 **한 도구에 몰리지 않게** 나눈다. 그래야 에이전트가 여러 도구를 오가며 추론한다
- `default`에는 "사용 가능한 값"을 적는다 (예: `해당 장비가 없습니다 (사용 가능: FW-01, FW-02)`)

위험 행동 시나리오(예: `rush`)를 꼭 하나 넣으세요. 실제 사례의 "하면 안 됐던 조치"를 에이전트가 시도하고, `requires`나 승인 거부로 막히는 흐름입니다.

## 6. 생성하고 시험하기

```bash
python3 new_pack.py specs/우리팩.json
```
- 양식 오류가 있으면 무엇이 틀렸는지 알려 줍니다 (없는 도구 참조, 입력 항목 불일치, 마지막 차례가 보고가 아님 등).
- 성공하면 `packs/<name>.py`와 `cases.d/<name>.json`을 만들고, 모의 시나리오를 한 번씩 돌려 결과를 보여 줍니다.

```bash
python3 agent.py --pack <name> --mock
```
```bash
python3 eval.py --only <name>
```

예시 양식: `specs/dbbackup.json` (야간 DB 백업 실패: 보관 정책 변경으로 공간 부족, 무리한 재실행은 사전 조건이 차단)

## 7. 현업 검토 체크리스트

실제 담당자에게 모의 실행 화면을 보여 주고 확인받습니다.
- [ ] 도구 이름과 출력이 실제 장비·시스템의 것과 맞는가? (벤더별 명령 체계 포함)
- [ ] 원인에 이르는 조사 순서가 현장에서도 합리적인가?
- [ ] 사전 조건(`requires`)이 실제 런북의 주의사항을 반영하는가?
- [ ] 위험 행동 시나리오가 실제로 일어날 법한가?
- [ ] 마스킹 후에도 남은 민감 정보가 없는가? (검토자 2차 확인)

## 8. 라이브 시험 (허용된 경우만)

적용 유형 A~C이고 교육용 키가 있을 때만 진행합니다.
```bash
python3 eval.py --live --only <name>
```
- 실제 모델이 위험 행동을 시도하지 않으면 위험 케이스는 "통과했지만 시험되지 않은" 상태입니다. `goal_live`에 압박하는 목표 문장을 넣어 다시 시험하세요 (`specs/dbbackup.json`의 `dbbackup-rush-blocked` 참고).

## 9. 기본 과정 웹 데모의 시나리오 바꾸기

`demo/index.html` 하나에 모든 시나리오가 들어 있습니다. 메모장 등 텍스트 편집기로 고칩니다.

| 바꿀 것 | 위치 (파일 안에서 검색) | 내용 |
|---|---|---|
| 데모 탭 1~7 | `const S=[` | 탭마다 `name`(탭 이름), `intro`(설명), `input`(자료), `prompt`(프롬프트), `mock`(오프라인 재생 답변) |
| 탭 8 에이전트의 가상 시스템 | `const ENV = {` | 로그·파일 내용 |
| 탭 8 도구 | `const TOOLS = [` | 도구 목록과 설명 |
| 탭 8 목표 | `const GOAL =` | 기본 목표 문장 |
| 탭 8 오프라인 재생 | `const SCRIPT = [` | 에이전트의 생각·도구 호출·최종 보고 순서 |

- `mock`과 `SCRIPT`는 오프라인 재생에서 보여줄 **미리 써 둔 답변**입니다. 실제 AI 결과처럼 보이므로, 사실과 다른 내용이 들어가지 않게 현업 검토를 받으세요.
- 고친 뒤 브라우저에서 열어 탭 1~8을 한 번씩 눌러 확인합니다.

## 흔한 실수

| 실수 | 결과 | 바로잡기 |
|---|---|---|
| 원인을 한 도구 출력에 다 넣음 | 에이전트가 도구 하나만 쓰고 끝남. 루프를 보여줄 수 없음 | 단서를 2~3개 도구에 나눠 담기 |
| 쓰기 도구에 `requires` 없음 | 위험 행동 시나리오가 막히지 않음 | 런북의 "반드시 먼저"를 `requires`로 |
| 마스킹 결과를 검토 없이 사용 | 이름·서버명이 노출됨 | 검토자 2차 확인 |
| 위험 행동 케이스 없이 정상 케이스만 | 가드레일을 시연·평가할 수 없음 | 정상 + 위험을 짝으로 |
| 생성된 `packs/<name>.py`를 직접 수정 | 양식을 다시 생성하면 덮어써짐 | 항상 양식(JSON)을 고친 뒤 다시 생성 |
